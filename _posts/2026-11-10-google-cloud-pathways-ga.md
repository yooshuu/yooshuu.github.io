## 1. 규모가 커질수록 조정이 문제가 되는 이유

Google은 이 문제의 핵심을 연산량이 아니라 **조정**으로 봅니다. 무엇을 어디서, 어떤 순서로 실행하고, 텐서를 어떻게 옮기며, 장애를 어떻게 견디느냐의 문제입니다.

통신 대역폭의 차이가 그 배경입니다. Google이 예로 든 TPU v5p는 같은 그룹 안의 칩끼리는 양방향 1,200GB/s로 연결되지만, 데이터센터 네트워크로 나가는 대역폭은 50Gb/s, 약 6GB/s입니다. 학습 단계마다 집합 통신을 기다려야 하는 SPMD에서는 그룹 수가 늘수록 통신 시간도 늘고, 처리량은 가속기 수에 비례해 늘지 못합니다.

Google은 SPMD의 결과를 다음 세 가지로 정리합니다.

- 기계 한 대가 실패하면 작업 전체가 멈추고, 실행 중에 장치를 더하거나 뺄 수 없습니다.
- 작업은 끝날 때까지 가속기를 붙잡고 있어, 작업 안에서 노는 칩도 다른 곳에 쓰이지 못합니다.
- 각 작업자는 자기 장치만 보기 때문에 전체 작업을 한눈에 보며 디버깅하기 어렵습니다.

## 2. 클라이언트 하나가 전체를 지휘하는 구조

Pathways에서는 일반 CPU 머신에서 도는 Python 클라이언트 하나가 처음부터 끝까지의 계산을 정의합니다. 코드는 실제 칩이 아니라 **가상 장치**를 대상으로 쓰고, 리소스 관리자가 이를 물리 칩에 연결합니다. 각 블록은 컴파일된 SPMD 프로그램이 되고, 블록 사이를 오가는 텐서는 런타임이 전달합니다. 서로 다른 그룹에서 여러 프로그램이 함께 도는 이 방식을 Google은 MPMD라고 부릅니다.

런타임은 실행 효율을 위해 세 가지 장치를 씁니다.

| 장치 | 설명 |
| --- | --- |
| 비동기 디스패치 | 입력의 모양과 자료형을 미리 알기 때문에, 앞 단계 출력이 나오기 전에 버퍼와 전송 일정을 잡아 둡니다. |
| 중앙 스케줄러 | 여러 프로그램에 하나의 일관된 실행 순서를 정해, 통신하는 연산이 함께 시작되고 교착 상태에 빠지지 않게 합니다. |
| 장애 시 재배치 | 호스트가 고장 나면 작업을 다시 띄우지 않고 정상 칩으로 옮깁니다. Google은 이를 탄력적 학습의 바탕으로 소개합니다. |

칩이 준비되기 전에 컴파일을 시작할 수 있어 준비 시간이 겹쳐진다는 점도 특징입니다. 같은 Python 프로세스가 호스트 하나에서도, 수천 개에서도 그대로 동작하며, 대화형 셸에서 중단점을 걸어 디버깅할 수도 있습니다.

## 3. Pathways on Cloud의 구성 요소

공식 문서는 Pathways on Cloud를 다음 요소로 설명합니다. 가속기가 필요한 것은 작업자뿐이고 나머지는 CPU에서 돕니다.

- **리소스 관리자:** 가속기를 작업에 나누어 주고, 작업자 상태를 감시하며, 스케줄링과 일시 정지, 재개를 맡는 제어 평면입니다.
- **Pathways 클라이언트:** 프로그램이 보낸 연산을 받아 컴파일된 프로그램을 어디서 실행할지 정합니다.
- **Pathways 작업자:** TPU VM에서 컴파일된 실행 파일을 받아 실제 계산을 수행합니다.
- **IFRT 프록시 클라이언트와 서버:** 사용자 코드와 Pathways 사이를 잇습니다. JAX는 기본 멀티 컨트롤러 런타임 대신 이 프록시 클라이언트를 사용합니다.
- **사이드카 서버:** 작업자와 같은 가속기 VM에서 사용자가 지정한 Python 코드를 실행해 데이터 전송 지연을 줄입니다.

실행 환경은 GKE와 Slurm 기반 Cluster Director 클러스터이며, 컴파일 캐시 같은 임시 파일을 담을 Cloud Storage 버킷이 필요합니다.

## 4. 정식 출시 범위와 Ray와의 관계

정식 출시된 것은 Pathways on Google Cloud이며, TPU에서 JAX 프로그램을 실행합니다. 여러 클라이언트가 클러스터 하나를 나눠 쓰는 **Shared Pathways Service**도 블로그에서 소개되었는데, GKE 위 TPU에서 상시 서비스로 돌며 클라이언트가 접속할 때 슬라이스를 받고 접속을 끊을 때 반납하는 방식입니다. 블로그가 연결한 이 서비스의 코드는 pathways-utils 저장소의 `experimental` 경로에 있어, 정식 출시 범위와는 구분됩니다.

Ray와의 관계도 짚었습니다. Google에 따르면 Ray는 클러스터 위에서 Python AI 작업을 조율하지만, 칩 위에서 학습이 실행되는 방식은 바꾸지 않습니다. Ray의 각 작업자는 여전히 SPMD로 돌고 자기 장치만 봅니다. Google은 Ray를 조율 계층, Pathways를 실행 계층으로 나누어 두 도구를 함께 쓸 수 있는 관계로 설명합니다.
