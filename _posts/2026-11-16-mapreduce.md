검색창에 낱말 하나를 치면 결과가 거의 바로 뜹니다. 검색할 때마다 전 세계 웹 페이지를 뒤지는 것이 아니라, 어떤 낱말이 어느 페이지에 있는지 적어 둔 표(색인)를 미리 만들어 두기 때문입니다. 문제는 이 표를 만드는 일이 컴퓨터 한 대로는 도저히 끝나지 않는다는 점입니다. 구글은 이 일을 **맵리듀스(MapReduce)**로 해결했다고 2004년 논문에서 밝혔습니다. 큰 데이터를 여러 컴퓨터에 나눠 맡기고, 각자 처리한 결과를 다시 모으는 방법입니다.

<div class="summary" markdown="1">
**한눈에 보기**

- 맵리듀스는 큰 데이터를 여러 컴퓨터가 **나눠서 처리하고 다시 모으는** 방법입니다.
- 일은 **맵(나눠서 세기) → 셔플과 정렬(같은 것끼리 모으기) → 리듀스(합치기)** 순서로 흘러갑니다.
- 하둡에서는 HDFS가 데이터를 저장하고, YARN이 일할 컴퓨터를 정하고, 맵리듀스가 계산합니다.

## 1. 문장 세 줄로 따라가 보기

말로만 들으면 감이 잘 안 오니, 아주 작은 예로 직접 세어 보겠습니다. 문장 세 줄이 컴퓨터 두 대에 나뉘어 있고, 낱말마다 몇 번 나왔는지 알고 싶은 상황입니다.

| 컴퓨터 | 가진 문장 |
| --- | --- |
| A | 사과 바나나 사과 |
| A | 포도 사과 |
| B | 바나나 포도 포도 |

**① 맵: 각자 자기 몫부터 셉니다.** A와 B는 서로 기다리지 않고 동시에 자기 문장을 낱말로 자릅니다. 그리고 낱말이 나올 때마다 "1번 나왔다"는 짝을 하나씩 만듭니다.

- A: `(사과, 1)` `(바나나, 1)` `(사과, 1)` `(포도, 1)` `(사과, 1)`
- B: `(바나나, 1)` `(포도, 1)` `(포도, 1)`

**② 셔플과 정렬: 같은 낱말끼리 모읍니다.** 이제 A에서 나온 짝과 B에서 나온 짝을 섞어, 같은 낱말끼리 한곳에 모으고 가나다순으로 줄을 세웁니다. 이 단계는 사람이 손댈 필요 없이 시스템이 알아서 해 줍니다.

- `(바나나, [1, 1])`
- `(사과, [1, 1, 1])`
- `(포도, [1, 1, 1])`

**③ 리듀스: 모은 것을 더합니다.** 낱말마다 붙은 1을 다 더하면 끝입니다.

- `바나나 2`, `사과 3`, `포도 3`

문장이 수억 줄이고 컴퓨터가 수천 대여도 하는 일은 이것이 전부입니다. 이 과정에서 사람이 직접 짜는 코드는 **맵 함수와 리듀스 함수 두 개뿐**입니다. 일을 나누고, 맡기고, 모으는 나머지 일은 다른 누군가가 대신 맡아 줘야 합니다.

## 2. 맵리듀스가 생긴 이유

컴퓨터 여러 대로 일을 하면 계산 말고도 신경 쓸 것이 한둘이 아닙니다. 누가 어느 부분을 맡을지 정해야 하고, 수천 대쯤 되면 그중 몇 대는 늘 고장 나 있거나 느립니다. 프로그램을 짤 때마다 이런 것을 일일이 챙기다 보면, 정작 하고 싶던 계산보다 관리 코드가 더 길어지기 일쑤입니다.

구글의 제프리 딘과 산제이 게마왓이 2004년 논문에서 내놓은 답이 맵리듀스입니다. 귀찮은 관리 일은 라이브러리가 한꺼번에 떠맡고, 프로그래머는 "무엇을 셀지"만 쓰면 되게 만든 것입니다. 논문이 나올 무렵 구글에서는 이런 작업이 하루에 천 개 넘게 돌아가고 있었습니다. 하둡에도 이 관리를 전담하는 프로그램이 따로 있습니다.

## 3. 하둡 안에서 일이 흘러가는 순서

하둡에서 맵리듀스를 돌리면 세 부분이 일을 나눠 맡습니다.

| 부분 | 하는 일 |
| --- | --- |
| HDFS | 데이터를 블록 단위로 쪼개 여러 컴퓨터에 저장합니다. |
| YARN | 컴퓨터마다 메모리와 CPU가 얼마나 남았는지 보고, 어디서 일할지 정합니다. |
| 맵리듀스 | 맵과 리듀스로 실제 계산을 합니다. |

용어 두 개만 먼저 짚겠습니다. 낱말 세기처럼 사용자가 맡긴 일 전체는 **잡(job)**, 그 잡을 잘게 쪼갠 맵 작업과 리듀스 작업 하나하나는 **태스크(task)**라고 합니다. 잡 하나를 실행하면 이런 일이 차례로 일어납니다.

1. 세어야 할 파일은 이미 HDFS에 블록으로 나뉘어 들어가 있습니다.
2. 잡을 실행하면 YARN이 이 잡만 전담할 관리 프로그램, **MRAppMaster**를 하나 띄웁니다.
3. MRAppMaster는 YARN에 일할 자리(컨테이너)를 달라고 요청한 뒤, 맵 태스크와 리듀스 태스크를 여러 컴퓨터에 나눠 줍니다. 맵 태스크는 대개 블록 하나당 하나씩 생깁니다.
4. 태스크는 저마다 **YarnChild**라는 별도 프로그램으로 실행됩니다. 따로따로 돌기 때문에 하나가 탈이 나도 나머지는 멀쩡하고, 일이 끝나면 알아서 사라집니다.
5. 맵, 셔플과 정렬, 리듀스를 다 거친 결과는 다시 HDFS에 저장됩니다.

MRAppMaster는 잡이 끝날 때까지 태스크들을 지켜보다가, 실패한 것이 있으면 다시 돌립니다. 여기까지만 보면 깔끔합니다. 하지만 컴퓨터가 수천 대로 늘어나면 이 순서 곳곳에서 새로운 문제가 튀어나옵니다.

## 4. 심화: 컴퓨터가 많아지면 생기는 문제들

**데이터는 어느 컴퓨터가 읽을까?**
하둡은 큰 파일을 보통 128MB짜리 조각(블록)으로 잘라 여러 컴퓨터에 흩어 놓습니다. 혹시 모를 고장에 대비해 조각마다 복사본도 흔히 세 개씩 둡니다. 맵 작업은 그 조각을 이미 갖고 있는 컴퓨터에서 실행됩니다. 1절에서 A의 문장은 A가, B의 문장은 B가 센 것과 같습니다. 덩치 큰 데이터를 옮기는 것보다 "세는 일"을 데이터 쪽으로 보내는 편이 훨씬 빠르기 때문입니다. 다만 이렇게 하면 맵 결과도 여러 컴퓨터에 흩어진 채로 나옵니다.

**흩어진 결과에서 같은 낱말은 어떻게 한곳에 모일까?**
결과를 합치는 리듀스도 여러 대가 나눠 맡습니다. "사과는 누가 더할지"도 미리 정해 둬야 합니다. 하둡은 낱말을 정해진 규칙으로 계산해 번호를 매기고, 그 번호로 담당 리듀스를 고릅니다. 같은 낱말은 언제 계산해도 같은 번호가 나오므로, A에서 나온 "사과"든 B에서 나온 "사과"든 결국 같은 리듀스에 도착합니다. 이 담당을 정해 주는 부분이 **파티셔너**입니다.

**다른 컴퓨터로 보낼 때는 어떤 모양으로 보낼까?**
컴퓨터 안에 있는 데이터를 그대로 네트워크에 실어 보낼 수는 없습니다. 0과 1이 한 줄로 늘어선 모양(바이트)으로 펴서 보내고, 받는 쪽에서 다시 원래 모양으로 조립해야 합니다. 펴는 쪽을 **직렬화**, 다시 조립하는 쪽을 **역직렬화**라고 합니다. 자바의 `int`나 `String` 같은 기본 타입은 이런 전송에 잘 맞지 않아서, 하둡은 `IntWritable`, `Text` 같은 전용 타입을 따로 씁니다.

**주고받는 도중에 컴퓨터가 고장 나면?**
관리 담당이 일하는 컴퓨터들에 주기적으로 "살아 있니?" 하고 물어봅니다. 대답이 없으면 그 컴퓨터가 하던 태스크를 다른 컴퓨터에 다시 맡깁니다. 하둡에서는 3절의 MRAppMaster가 바로 이 역할을 합니다. 구글 논문에는 컴퓨터 약 80대가 몇 분 동안 한꺼번에 연결이 끊겼는데도 작업을 끝까지 마친 사례가 나옵니다.

**고장은 아닌데 한 대만 유난히 느리면?**
다른 컴퓨터가 다 끝내도 한 대가 늦으면 전체가 그 한 대를 기다려야 합니다. 맵리듀스는 작업이 거의 끝나 갈 즈음, 남은 일을 다른 컴퓨터에도 똑같이 시켜 두고 먼저 끝난 쪽 결과를 씁니다. 논문의 정렬 실험에서 이 기능을 꺼 봤더니 시간이 44%나 더 걸렸습니다.

## 5. 실제로 쓰인 곳

가장 유명한 예는 처음에 이야기한 구글 검색 색인입니다. 구글은 색인을 만드는 시스템을 맵리듀스로 새로 짰습니다. 20TB가 넘는 문서를 5~10번의 맵리듀스 작업으로 처리했고, 한 단계의 코드는 약 3,800줄에서 700줄로 확 줄었습니다. 예전에는 몇 달 걸리던 수정이 며칠이면 끝났다고 합니다.

논문에는 이런 쓰임도 함께 소개돼 있습니다.

- **분산 grep:** 어마어마한 양의 문서에서 특정 문장이 들어간 줄만 골라냅니다.
- **URL 접속 빈도:** 웹 접속 기록을 뒤져 주소별로 몇 번 열렸는지 셉니다.
- **역색인:** 책 뒤의 찾아보기처럼, 낱말마다 그 낱말이 나오는 문서 목록을 만듭니다.
- **분산 정렬:** 아주 큰 데이터를 키 순서대로 줄 세웁니다.

클라우드에도 이름이 남아 있습니다. AWS의 빅데이터 서비스인 Amazon EMR은 원래 이름이 **Amazon Elastic MapReduce**였습니다. 지금은 하둡과 스파크 같은 도구를 대신 운영해 주는 서비스입니다.

반대로 맵리듀스를 다른 방식으로 바꾼 곳도 있습니다. MongoDB는 5.0부터 자체 map-reduce 기능을 더는 권하지 않고, 성능도 좋고 쓰기도 편한 집계 파이프라인(aggregation pipeline)을 쓰라고 안내합니다.
